## Shared engine and filesystem

All modules are in `docs/assets/javascripts/linux-terminal/`:

- `filesystem.mjs` owns the only virtual filesystem. It resolves case-sensitive absolute/relative paths component by component, checks ancestor search permission, maintains ownership/modes/timestamps, and provides shared read/write/list/creation plus copy/move/remove/chmod/chown operations. Directory read permission lists names; search permission permits accessing children. Long listings check access to each child's metadata. New copies belong to the effective user, use source permissions subject to the fixed 022 creation policy, and have independent nodes. Existing file copies retain destination ownership/mode. Moves preserve subtrees and metadata, update current/previous directory paths, and need parent permissions rather than source-file write permission.
- `parser.mjs` retains Phase 1 quoting, escaping, home/environment expansion, comments, and redirection protections. It never evaluates student text. Shell pipes, wildcard expansion, chains, substitutions, and interactive standard input remain unsupported. Quote find patterns so the shell passes them to find.
- `file-commands.mjs` registers handlers in the existing shell dispatcher. It is not another shell or filesystem. It implements transfer operands, limited text search, bounded wildcard matching, permission modes, and root/student/numeric identity parsing.
- `shell.mjs` dispatches all commands (including commands wrapped in sudo) through the same package-availability check and existing VFS and returns stdout/stderr/status plus optional manual/editor actions. Nano's action contains a buffer referencing this VFS. Interactive Nano/clear output redirection is rejected before opening a destination file. Other output redirection preserves Phase 1 shell open/truncate-before-dispatch behavior.
- `manuals.mjs` documents only implemented syntax. `--help` returns the same concise help inline for supported commands other than echo.
- `nano.mjs` provides `NanoSession` and the view mounted inside the original terminal. The buffer uses the shell's VFS; opening a new name creates no filesystem node. Saving uses the same permission/size checks as shell redirection. A native multiline text area supplies ordinary editing, cursor navigation, selection, undo, and copy/paste, styled as a Nano terminal buffer. Ctrl+O prompts for the filename; Enter writes; Ctrl+X handles Save/Discard/Cancel; Ctrl+G opens concise help. Touch controls offer the same operations. Failed saves retain the buffer and filename prompt. New nonempty text receives Nano's normal final newline. Unsaved edits trigger the browser's unload warning; unsaved buffers themselves are not restored after navigation. Reset and profile selection are disabled while an editor is active. This is one buffer, not full GNU Nano emulation.
- `terminal.mjs` preserves the original transcript, command recall, completion, dialogs, theme controls, safe text rendering, and storage notices, and switches visibility between that terminal and Nano. Nano saves invoke the same workstation persistence function.

## Supported file operations and permissions

- `cp [-r] SOURCE ... DESTINATION`: independent file copies, recursive directory copies, existing-directory merge rules, and multiple-source targets. Self-copy and copying a directory into a descendant are refused. Unsupported preservation/interactive options are not claimed.
- `mv SOURCE ... DESTINATION`: file rename/overwrite, directory-tree moves, and multiple sources into an existing directory. A conflicting directory must be empty. Parent-to-descendant moves and replacing an active working directory are refused.
- `rm [-rf] PATH ...`: file deletion, recursive removal, missing-path suppression with `-f`, and sticky-directory ownership restrictions. Force never bypasses permissions. There are no simulated write-protection prompts. Each recursive operand is preflighted before deletion, so permission failure leaves that subtree intact; separate successful operands still apply. This differs from GNU rm's possible partial traversal effects and is stated in the short manual. Workstation foundation directories and the current directory/ancestors have explicit **simulator safety** restrictions. Removing an old working directory clears its stale previous-directory reference.
- `chmod MODE FILE ...`: three/four-digit octal modes and explicit `u/g/o/a` symbolic `+/-/=` operations with `rwx`, including comma-separated clauses. Owner/root authorization and parent traversal apply. Mode changes affect subsequent reads, writes, listing, traversal, copies, and removal. File execute/set-ID bits are represented; executing binaries/scripts is not implemented. No recursive chmod or ACLs are supported.
- `chown USER[:GROUP] FILE ...`: root/student names and numeric IDs. A different owning user requires root. An owner can retain their own ID and select one of their groups, matching ordinary authorization rules. Set-ID bits clear when identity changes. Student-facing elevation now uses the fictional sudo policy. Authorization is shared with every other VFS operation.
- `grep [-in] PATTERN FILE ...`: searches saved text, with case folding, line numbers, multi-file prefixes, and exit status 0/1/2 for match/no match/error. This subset accepts plain text; regular-expression metacharacters are explicitly rejected. No JavaScript regular expressions run from student patterns. Sample application/authentication logs accompany the original support log.
- `find [PATH ...] [-name PATTERN] [-type f|d]`: recursive permission-aware traversal, filename `*`/`?` matching, and AND combination of these two predicates. Root entries and hidden entries participate. No matches is successful; traversal failure is nonzero and preserves accessible results. Unsupported predicates, escapes, and bracket classes are rejected.

## Administration, processes and storage

- `system-state.mjs` defines the two account identities, fictional password-free sudo authorization, locked direct-root policy, process records, machine snapshot and volume accounting helpers. These objects are simulator state, never browser/host measurements.
- `system-commands.mjs` extends the existing registry. `sudo` scopes an effective VFS actor with `try/finally`, including errors and nested calls; it never permanently replaces the session user. A captured VFS actor lets `sudo nano` read/save as root throughout the buffer lifetime. Closing the editor revokes that buffer's authority and prevents later saves. Shell redirection is opened before sudo dispatch by the original shell, matching `sudo echo text > /etc/hosts` denial. Interactive command redirection is rejected before truncating a target, including commands wrapped in sudo.
- `sudo -l` describes the training authorization. Student is authorized, root is already privileged, and an unauthorized account/policy is denied. No password entry or actual OS credentials exist. `su` accepts only root/student and an optional leading `-` or `-l`. Ordinary root login fails; `sudo su -` creates a login shell in `/root`. Nested shells retain the previous user, current/previous directory, and shell PID. `exit` restores that context and removes the child process. The original student shell remains open. Nesting is bounded to 16. Foundation, mount, and suspended-working-directory protections keep saved sessions restorable.
- `ps`, `ps -e`, `ps -ef`, and `ps aux` derive from the same process table as `top`. The initial Mint image includes systemd, NetworkManager, Cinnamon, and student Bash; Fedora uses a gnome-shell record instead of Cinnamon. There is no SSH-service claim. Account switches add stable child Bash PIDs; exits remove them and future shells receive new IDs. Snapshots omit transient command processes. `top` uses the existing accessible terminal viewer, exits with q/Escape/Ctrl+C or the return button, and supports `top -b -n 1` inline/redirection. Its uptime is fixed at 2:01, memory at 4 GiB, and CPU/memory/task totals derive from modeled records. No timed updates or host metrics are claimed.
- `du [-hs]` recursively accounts for actual UTF-8 file text rounded up to a 1-KiB block per file; empty files and directories consume zero modeled data blocks. Default output uses 1-KiB units, `-h` formats units, and `-s` suppresses descendant lines. Traversal requires directory read/search permission; metadata size does not require reading file content. Denied subtrees report errors while retaining accessible partial totals.
- `df [-h] [PATH ...]` selects mounted volumes or the filesystem containing each path. Root `/dev/sda1` is 32 GiB with a fixed 4-GiB system-image allocation. Secondary `/dev/sdb1` is 1 GiB with 1 MiB fixed metadata allocation. Used equals fixed allocation plus the same modeled file blocks as du; available equals capacity minus used, with no reserved blocks. Percentage rounds up. Writes/copies and cross-volume moves check capacity. Human-readable totals are rounded display values; exact default 1-KiB columns balance.
- `mount` lists current mounts for any account. Root may mount the known secondary ext4 volume only at an existing, empty, unused `/mnt/training-disk`. That designated-point/empty-directory restriction bounds the simulator; arbitrary devices, alternate paths, options, and filesystem types are rejected. The volume starts with README.txt and a student-writable Reports directory. On mount, its nodes join the single VFS namespace. On unmount, they return to the volume's detached node map; the original empty mount-point metadata returns. There is no second shell/filesystem engine. `df` excludes detached volumes while `fsck -n` can inspect them.
- `umount DEVICE|DIRECTORY` requires root. The current directory of any active or suspended shell makes a volume busy. Mounted points/ancestors cannot be moved or removed; root cannot be unmounted. Stale previous-directory references into a detached volume are cleared. Both mounted and detached contents, ownership, modes, and mount/session/process state survive browser refresh. Reset restores student identity, original process records, and an unmounted clean training volume.
- `fsck -n DEVICE` is explicitly read-only and limited to the known, unmounted ext4 model. It reports recognized volume identity, modeled directory/parent consistency, file/directory counts, and allocated data blocks. Mounted volumes are refused in this simulator, including root; actual filesystem-specific checker behavior may differ. Repairs and actual ext4 internals are not simulated. Unknown devices and repair requests fail; there is no fake successful repair.

## Network and package management (Phase 3B)

The existing shell registers `network-commands.mjs` and `packages.mjs`; there is one terminal, parser, permission system, and VFS implementation. `network-state.mjs` owns the shared deterministic topology and pure lookup/routing/HTTP helpers. ### Shared network

The initial configuration remains enp0s3, 192.0.2.10/24, and default gateway 192.0.2.1. Loopback is fixed at 127.0.0.1/8. IPv4 configuration is bounded to reserved documentation ranges and a physical 192.0.2.0/24 LAN. Interface state, assigned addresses, connected prefixes, default-route availability, usable next hop, DNS services, endpoint reachability, ICMP echo response, and HTTP service availability are distinct state. Gateway reachability affects off-LAN traffic. A destination marked unreachable cannot return a final traceroute probe.

Up to three nameserver entries are tried until a reachable DNS service answers. `ping`, `curl`, and `traceroute` first consult readable `/etc/hosts`, then DNS; short hostnames use supported `search`/`domain` suffixes for training names. `dig` queries DNS directly and requires a full training name, so a hosts-file override does not change its answers. Resolver edits saved with elevated Nano immediately affect subsequent queries. The bounded resolver does not implement caching, arbitrary NSS modules, public DNS, IPv6 networking, or the full resolv.conf grammar.

### Implemented syntax

- `ip addr`, `ip addr show`, `ip -br addr`, `ip link show`, `ip route`, `ip route show` derive output from state. Root can use `ip link set enp0s3 up|down`, `ip addr add|del ADDRESS/PREFIX dev enp0s3`, `ip route replace default via GATEWAY dev enp0s3`, and `ip route del default`. Address changes are additive/removable, limited to four documentation-range IPv4 host addresses with prefixes 1..30. Gateways must be other on-link host addresses. Unknown interfaces, unsupported options, invalid/duplicate addresses, and off-link gateways fail before changing state. Assigning a remote server’s address locally makes that address local, rather than retaining a second fictional HTTP service there.
- `ping -c COUNT DESTINATION` requires 1..10 packets. Successful replies include sequences, TTL, deterministic RTTs and computed summary statistics. No replies return status 1; lookup/configuration errors return 2. Loopback continues working with the external interface down. ICMP echo loss does not imply that HTTP or other traffic is unavailable.
- `dig [@RESOLVER_IPV4] NAME [A|TXT] [+short]` reads the shared DNS records, with TTL/status/answer/server fields or short answers. NXDOMAIN and SERVFAIL responses are completed queries (status 0); unreachable resolvers return status 9. DNS can answer for a destination whose host or HTTP service is down. Other record types/options are rejected.
- `traceroute DESTINATION` prints up to five deterministic hops with RTTs or `* * *`. Silent intermediates can precede a responding destination. A trace that exhausts its hop budget can return status 0; students must inspect the hops. DNS/local-route errors are nonzero. Probe types/options are not otherwise emulated.
- `curl [-I] [-o FILE] http://HOST/PATH` supports modeled GET bodies and HEAD headers. Saved responses use the shared permission, ownership, capacity and persistence checks and can be opened in Nano. Unknown paths on a working service return HTTP 404; the status service returns 503; neither is a failed curl process without a fail option (not implemented). Errors include unsupported protocol (1), syntax (2/3), DNS/outside destination (6), connection (7), timeout (28), and file write (23). No HTTPS/TLS, credentials, alternate ports, query strings, fragments, redirects, arbitrary URLs, or actual network transfers are implemented. HTML bodies remain inert text.
- `apt list --installed`, `apt show PACKAGE`, `apt search TERM`, `sudo apt update`, `sudo apt install PACKAGE ...`, and `sudo apt remove PACKAGE ...` operate only in Mint. Updating advances the modeled index revision without changing installed versions. Installation/removal update actual installed flags. At most ten package operands are accepted; unknown/protected/unavailable-package failures are checked before committing changes. No-match searches and already-installed/not-installed operations have useful output.
- `dnf list installed`, `dnf info PACKAGE`, `dnf search TERM`, `sudo dnf install PACKAGE ...`, and `sudo dnf remove PACKAGE ...` operate only in Fedora DNF practice. The separate inventory uses Fedora-family package names such as `bind-utils`, `iproute`, `iputils`, and `procps-ng`, rather than Mint’s `dnsutils`, `iproute2`, `iputils-ping`, and `procps`. DNF is not presented as Mint-native; entering dnf in Mint fails without changing profiles.

Each inventory has 16 fictional package entries with name, version, description, protected/installed flags and repository availability. Versions are explicitly labeled training values. `traceroute`, `curl`, and DNS utilities are initially installed and optional; removal disables their supplied commands through the shared dispatcher, including sudo. Reinstallation restores availability. `support-notes` is an initially absent fictional documentation package with no extra command. Nano, IP inspection, shell and recovery foundations are protected. Inspection uses the local catalog; new installs and APT index refreshes require the configured resolver, route and repository HTTP service to work. Removal does not require network access. The package manager does not depend on optional curl/dig CLI installation. Transactions finish immediately without confirmation prompts and explicitly do not model real downloads, dependencies, upgrades, or binary disk usage.

### Evidence and persistence

`Shell.dispatch` records a transient observation of the actual handler, operands resolved through the existing VFS, effective identity, affected paths and returned output. `Shell.execute` records evidence only after a zero exit status, so missing packages, bad syntax, partial multi-file errors, failed network commands and mere history entries cannot count as successful diagnostics. The safe denied-read exercise has a separate restriction-observed flag; it never counts as a successful read. An NXDOMAIN query can succeed as a DNS exchange, and curl without `-f` can succeed as an HTTP exchange that returns 503. These modeled results are explained in the task.

Nano records only successful filesystem writes, including a content fingerprint, its initial opened text and whether this is the first write of that editor session. This distinguishes a saved reopened revision from unsaved text or repeated saves within one session. Archive evidence fingerprints the matching backup when copied/moved. Storage-copy evidence similarly fingerprints the report actually copied to the mounted volume; validation inspects the real detached volume tree after unmounting. Files, permissions, package inventory and network usability are checked live, including at final handoff. Previously verified badges describe the prior checkpoint; students can recheck after edits, and handoff rejects a now-missing or changed requirement.

`state.progress.guided` is an optional version-1 record within the existing workstation version-4 save, not a separate storage key:

- `version`, `mode` (`free` or `guided`), monotonic `serial`.
- `run`: `workspace`, selected `stage`, unique `completed` stage IDs, allowlisted boolean `evidence`, nullable eight-character `nanoHash`, `backupHash` and `storageHash`.

The restore path validates the shape, profile-specific stage IDs, bounded workspace form, counters, completion IDs, evidence allowlist and fingerprints. Older version-1/2/3/4 workstation saves with no guided record still load through the existing migrations. The existing progress and full-workstation byte limits remain intact. Mint and Fedora keep separate records inside their already-independent saves; profile switching and blocked-storage in-memory retention keep using `ProfileStore`. Unrelated Hub storage remains untouched.
