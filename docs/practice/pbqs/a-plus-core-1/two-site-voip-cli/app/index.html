Compare evidence before changing settings

A functioning site gives you a baseline. Use several clues to explain the symptoms, then verify the repair.

Latency

Latency is packet travel delay. High delay makes conversation feel slow and can cause people to talk over one another. A consistently late packet is different from one whose arrival time varies widely.

ping reports round-trip time, which includes travel to the destination and back. One-way voice delay and round-trip delay are different measurements.

Jitter

Jitter is variation in packet arrival timing. Voice needs a steady flow of audio packets. Uneven arrival can produce robotic or choppy speech even when average delay and total capacity are usable.

A jitter buffer can smooth arrival timing, but has limits and adds delay. Compare jitter with latency and loss.

Packet loss

Packet loss means some packets fail to arrive. Missing audio packets can create gaps or broken speech. Packets that arrive late and packets that never arrive are different problems.

Loss near the local gateway plus increasing interface errors can point toward a local link. Loss only beyond the gateway calls for upstream investigation.

Bandwidth and congestion

Bandwidth is a connection's available capacity. Congestion occurs when traffic demand approaches or exceeds that capacity. Queues can increase latency and jitter; full queues may drop packets.

Short traffic bursts can disturb voice on an otherwise adequate link. Sustained demand beyond the link's capacity calls for removing the bottleneck or increasing capacity. Session count alone does not measure bandwidth usage.

Quality of Service (QoS)

QoS prioritizes delay-sensitive traffic such as voice and video during competing network activity. It can reduce the effect of congestion on calls.

QoS does not create additional bandwidth and does not repair a physically bad cable or port. Check whether the evidence supports prioritization, a local repair, or more capacity.

Verify the change

Record the original evidence, apply a suitable repair, and measure again. Check call quality as well as the local connection and upstream path.

In this activity, Apply & retest changes the simulated configuration. Subsequent commands reflect that change. Interface counters show a fresh observation window after a local-link repair.

Use the healthy site as a baseline

  • Does one site have much higher latency, jitter, or packet loss?
  • Are IP settings appropriate for each site's own network?
  • Is one workstation using Wi-Fi while the other uses Ethernet?
  • Do local interface errors or discards differ?
  • Is one link saturated by competing traffic?

Start with the same service target at both sites. Compare local gateways to separate local trouble from upstream trouble. A ping to the remote office crosses both sites' paths, so its result can be affected by either end.

Different sites normally have different subnets and gateways. A difference in IP addresses alone does not mean the addressing is wrong.

Command reference

CommandWhat it tells you
helpLists this activity's restricted commands and target aliases.
ipconfigShows local IP configuration, including address, subnet mask, and default gateway.
ipconfig /allShows detailed adapter, DHCP, and DNS configuration. Adapter identity helps distinguish Wi-Fi from Ethernet.
netstatShows active TCP connections. Extra sessions can be a clue to competing activity, but do not prove high utilization. Voice media often uses UDP and is not represented by this default TCP connection list.
netstat -eShows interface statistics such as bytes, packets, errors, and discards. Compare counters over time and against other evidence. Counter availability depends on the adapter.
ping <target>Tests reachability and basic round-trip response time. Variation is a clue; ping is not a professional VoIP jitter measurement system. Four test packets and a longer voice observation window can show different loss percentages.
tracert <target>Shows the network path and response timing at each hop. It can help locate where increased delay begins. A slow or silent intermediate hop alone does not prove forwarding trouble; compare later hops and the destination.
voipstatShows the activity's combined simulated call-quality and WAN telemetry.

About the simulated tools

voipstat is NOT a standard Windows command. It was created for this activity to display several call-quality metrics together. You cannot run it from a normal Windows command prompt.

The real commands above have simplified outputs here. gateway, remote, and voice are convenient target aliases in this simulation. In a real environment, use the actual address or hostname.

The activity terminals run a restricted JavaScript simulation. They do not execute operating-system commands.

Where real measurements come from

Softphone diagnostics, unified communications dashboards, voice gateways, session border controllers, and call-quality platforms can expose voice telemetry. Network monitoring and packet-analysis tools such as Wireshark provide additional evidence.
