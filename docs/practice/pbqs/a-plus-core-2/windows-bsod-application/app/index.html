Similar symptoms, different causes

A useful diagnosis connects the error, the change history, test results, and the behavior after repair.

1 · Stop errors and application failures

A Windows stop error means the operating system encountered a condition it could not safely continue through. Windows stops and may save a crash dump before restarting. An application can also terminate while the rest of Windows continues running.

A missing dependency can prevent one application from starting without causing a BSOD. Record the exact stop code or dialog, when the failure occurs, and whether Windows remains usable.

2 · Read a code as a clue

Stop codeWhat to investigate
VIDEO_TDR_FAILUREWindows could not recover from a display timeout. Investigate drivers, graphics hardware, power, cooling, and change history.
MEMORY_MANAGEMENTA serious memory-management error. RAM faults, unstable settings, or low-level software corruption can be involved.
IRQL_NOT_LESS_OR_EQUALInvalid memory access at an elevated interrupt level. Drivers and memory are possible causes.
INACCESSIBLE_BOOT_DEVICEWindows lost access to its boot device. Investigate storage drivers, configuration, and hardware.

A code does not identify a replacement part. A named module is another clue, not proof that the file itself is the only problem.

3 · Drivers, Safe Mode, and rollback

Kernel-mode drivers can affect the stability of the whole operating system. Compare the current provider, date, and version with the last stable configuration and the first failure.

Navigate Choose an option → Troubleshoot → Advanced options → Startup Settings → Restart → Enable Safe Mode. Safe Mode uses a limited set of drivers and services. A working Safe Mode session supports further investigation; it does not prove all hardware is healthy.

In Device Manager, select the device, open Properties, and use the Driver tab. Roll Back Driver restores an available earlier package. If rollback is unavailable, use a compatible, approved package from the manufacturer. Restart when required and test the original workload with the device enabled. Reinstalling the same faulty version may reproduce the failure.

4 · Events and reliability history

Event Viewer organizes records into logs. Read the source, event ID, time, and General details. BugCheck 1001 can record a Windows stop error. Kernel-Power 41 records an unexpected shutdown and does not establish its cause. Application Error 1000 can identify an application and faulting module.

Reliability Monitor, opened with perfmon /rel, helps compare failures with installations and other changes. Timing suggests a hypothesis to test. Old errors remain in history after a successful repair; verify that the original problem no longer occurs.

5 · Test memory before replacing it

Windows Memory Diagnostic, opened with mdsched.exe, restarts into a memory test. Review the later MemoryDiagnostics-Results event in the System log. A failed test indicates a memory-subsystem problem, but does not by itself isolate a module, slot, controller, or setting. A passing test is not an absolute guarantee against intermittent faults.

Compare capacity, type, speed, and manufacturer-approved settings. With the machine shut down, power disconnected, and ESD precautions in place, test modules individually using approved diagnostics. An error that follows a module across known-good slots supports a module fault. An error tied to one slot suggests investigating the board or slot.

After service, restore the required capacity, run a fresh diagnostic on the final configuration, and test normal operation. This activity varies which original module is defective. Its separate OEM bench test represents an authorized technician's isolation work, not a Windows Memory Diagnostic feature.

6 · Missing DLLs and runtimes

Applications depend on supporting files and shared runtimes. VCRUNTIME140.dll belongs to the Visual C++ runtime family. Check the application's requirements and installed packages. A 32-bit application needs its x86 runtime even when Windows is 64-bit; x64 and x86 packages can coexist.

Restore a required runtime through Microsoft or an approved signed installer. Do not fetch standalone DLLs from arbitrary download sites. Repairing an application may restore its own files while leaving shared prerequisites unchanged. A full vendor installer may include those prerequisites.

Once a dependency is restored, test again. An interrupted update may also have left application files inconsistent. Read new application events and repair or reinstall the app if the evidence supports it.

7 · SFC and DISM have a scope

Run system-integrity commands from an authorized administrator session. sfc /verifyonly checks protected Windows files; sfc /scannow checks and attempts repairs. DISM can inspect or repair the Windows component store that servicing uses.

DISM /Online /Cleanup-Image /ScanHealth
DISM /Online /Cleanup-Image /RestoreHealth
sfc /scannow

If Windows corruption is supported by evidence, DISM followed by SFC can be appropriate. Neither command guarantees restoration of a third-party application's files or runtime dependencies. Read the results instead of treating a success message as a universal fix. In WinRE, /Online refers to the running recovery image; installed Windows requires appropriate offline servicing parameters.

8 · Verify the repair you made

For a driver repair, return to normal startup and exercise the original graphics function. For memory service, confirm the intended configuration, inspect a fresh diagnostic result, and run the workload. For an application repair, launch it and test the function that mattered to the user.

Scheduling a test is not a test result. A basic-display workaround is not full graphics recovery. A successful application launch is not a completed export. Keep a short record of the evidence, change, and verification.

Use the Windows Command-Line Reference for additional syntax and result interpretation.
